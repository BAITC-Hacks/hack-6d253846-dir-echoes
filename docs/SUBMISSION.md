# Сдача решения HackAlem AI

Код и форма сдачи — две отдельные части результата. Участник должен сохранить итоговую версию в [выданном командном репозитории](https://github.com/BAITC-Hacks/hack-6d253846-dir-echoes) и отдельно отправить решение на платформе организатора.

Личный дедлайн готовности и сдачи: **17:50, Asia/Qyzylorda (UTC+5)**. Согласно скриншоту сообщения организатора, переданному участником, **оставаться на мероприятии нужно до 18:00, даже если решение уже готово**. Это разные контрольные точки; точное время в ранее предоставленных PDF не указано.

Адрес формы сдачи не предоставлен: открыть её через кабинет мероприятия, не подставлять предполагаемый URL.

## 1. Подготовить сдаваемый коммит

1. Выполнить проверки для актуального дерева:
   ```bash
   pnpm typecheck
   pnpm test
   pnpm build
   git diff --check
   git status --short
   ```
2. Убедиться, что исходные JSON/PDF, локальные отчёты, базы, ключи и коды доступа не включены в Git. Полный `report.json` / `dev_subset.json` остаётся вне репозитория; в README достаточно агрегированных результатов.
3. Проверить README как самостоятельную инструкцию: какую проблему решает продукт, технологии, запуск и шаги проверки. Шестишаговый маршрут для жюри уже добавлен; сверить его с интерфейсом итогового деплоя и указать границы внешних интеграций.
4. Создать финальный коммит и отправить в исходный репозиторий. Не переносить сдачу в другой репозиторий.
5. После push проверить совпадение:
   ```bash
   git fetch origin
   git rev-parse HEAD
   git rev-parse origin/main
   ```
6. Сохранить итоговый SHA и результаты проверок. `0661777` обозначает подтверждённую публикацию на момент этой записи; финальный SHA пока не зафиксирован.

Участник требует последующие commit/push каждые 45–50 минут до 17:50. Предоставленные правила не устанавливают минимальную частоту коммитов; регулярный push не заменяет финальную форму сдачи.

## 2. Проверить опубликованную версию

1. Открыть реальный адрес Vercel, войти участником и выполнить текстовый вопрос.
2. Проверить trace, сохранение разговора после перезагрузки, preview операции и явное подтверждение.
3. Отправить просьбу о специалисте; войти супервизором, принять, ответить и закрыть обращение.
4. Проверить живой микрофон: минимум три последовательные реплики через автоматическую паузу, слышимый ответ, возврат к прослушиванию, ручное «Перебить ответ» и остановку микрофона. Проверить RU, KK и их смешение; TR и новые пары принять отдельно. Не вводить реальные персональные данные.
5. Зафиксировать фактические результаты и ограничения. Успешный `/api/health` подтверждает только ответ приложения.
6. Внести проверенный адрес в README и форму мероприятия. Коды доступа передать жюри по предусмотренному закрытому каналу; не включать их в описание проекта.

**Production URL:** [dir-echoes-voice-router.vercel.app](https://dir-echoes-voice-router.vercel.app). Подтверждённая публикация — `0661777`. SHA итогового деплоя и результаты его голосовой приёмки: **ожидают записи**.

## 3. Сохранить решение на платформе организатора

1. В кабинете мероприятия открыть страницу треков / кейсов.
2. Выбрать свой кейс **Voice Router** и нажать **«Сдать решение»**.
3. Указать название, описание и именно выданный репозиторий.
4. Если поле предусмотрено, добавить фактически проверенный адрес приложения; заполнить остальные обязательные поля интерфейса.
5. Сохранить форму и проверить, что она связана с правильным кейсом и командой, а интерфейс подтверждает сохранение.
6. До дедлайна при изменениях обновить форму и проверить её повторно. Сам по себе push не подтверждает сдачу на платформе.

## Текст для полей проекта

**Название:** DIR ECHOES — Voice Router для контакт-центра.

**Описание:**

DIR ECHOES связывает свободную реплику с проверяемым действием контакт-центра: LLM выбирает один или несколько из 40 сценариев, сервер проверяет параметры и владение записями, сохраняет контекст и требует согласия перед изменением данных. Супервизор видит маршрут и действия, принимает очередь и продолжает диалог. В коде реализован голосовой цикл с одним стартом и автоматической отправкой реплики после паузы; STT обрабатывает отдельные реплики, а во время ответа микрофон приостановлен. Предусмотрены RU/KK/TR и конкретные сочетания языков; качество нового TR требует отдельной приёмки.

Стек: Next.js, TypeScript, PostgreSQL / Neon, OpenAI Structured Outputs, STT и TTS, Vercel. Исторический baseline ранней версии на 104 текстовых dev-репликах — 95,19% основного сценария и 93,27% полного совпадения; это не оценка последнего ядра или живой речи. Платёжные, SMS, телефонные и клинические подключения не предоставлены: система сохраняет запросы и явно показывает ожидание внешнего исполнения.

Перед вставкой сверить описание с финальным коммитом. Результаты публикации и живого голоса дописать только после их проверки.

## Данные и правила участия

Официальный набор используется с согласия участника и согласно ограничениям мероприятия. Исходные записи и документы не публикуются автоматически. Секреты хранятся в серверном окружении, рабочие данные закрыты входом, доступ к репозиторию сохраняется у команды и организаторов. Нагрузочное тестирование и сканирование инфраструктуры мероприятия не входят в проверку функций.

Участник принимает продуктовые решения и проверяет результат. По правилам зачёта: суммарные перерывы не более 60 минут, присутствие в последний час и до официального окончания, выходы через стюарда. Новое сообщение организатора на скриншоте уточняет присутствие **до 18:00 даже при готовом решении**. После мероприятия временные ключи и копии данных обрабатываются в согласованном с организатором порядке.
